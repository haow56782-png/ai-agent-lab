# 编码基线 — Paper Formatter

这份文档定义 `paper-formatter` 项目前后端共享的默认编码基线。它不是“理想状态清单”，而是日常实现、评审和重构时默认遵守的最低标准。

## 1. 架构思维

- 代码首先要表达职责边界、依赖方向和数据流，而不是只追求功能跑通。
- 控制器 / 路由层负责接收输入与输出响应。
- service / orchestration 层负责串联流程、调用依赖、组织副作用。
- domain-facing 模块负责业务规则、命名语义和核心模型。
- I/O、副作用、数据库、网络、存储都应位于边缘层，而不是散落在纯逻辑函数内部。

默认检查：

- 这个模块只承担一个清晰职责吗？
- 数据从哪里来、在哪里变化、最终流向哪里，读者能一眼看出吗？
- 当前模块依赖的是抽象边界，还是直接耦合到底层实现？

## 2. 单一职责原则（SRP）

- 一个函数、类、模块只做一件事，并把它做好。
- 函数长度通常应控制在一个屏幕内，经验上以 `30` 行左右为目标。
- 如果函数名自然出现 `and`，往往意味着职责过多。
- 一个函数内部的控制流应该尽量收敛，避免过多分支和跳出点。

示例：

- 不推荐：`createSchoolAndUpdateCacheAndSendEmailAndLog()`
- 推荐：`createSchool()`、`refreshProfilesCache()`、`sendNotificationEmail()`、`logger.info()`

## 3. 显式优于隐式

- 参数、返回值、状态变化都应显式表达。
- 尽量不用隐式 `this` 绑定、隐式闭包状态、隐式副作用。
- 纯计算逻辑应优先做成纯函数：相同输入产生相同输出。
- 副作用函数要让读者一眼知道它会访问网络、数据库、存储或时间系统。

默认检查：

- 这个函数是否依赖了调用者看不见的外部状态？
- 这个变量的来源是否需要读完整个文件才能知道？
- 这段逻辑是纯变换，还是混入了副作用？

## 4. 防御性编程

- 永远假设外部输入可能异常、依赖可能失败、边界可能为空。
- 所有外部输入都要校验类型、长度、格式和必要字段。
- 访问可空对象前先检查 `null / undefined`。
- 避免 `any`，优先使用 `unknown` 加类型守卫。
- 所有异步边界都应有明确错误处理。

示例：

```ts
function getName(user: unknown): string {
  if (!user || typeof user !== 'object' || !('name' in user)) {
    return '';
  }
  return String(user.name);
}
```

## 5. 开闭原则（OCP）

- 对扩展开放，对修改关闭。
- 新增能力时，优先新增实现，而不是把原有逻辑改成更长的 `if / else`。
- 稳定的是接口边界，不稳定的是具体实现。
- 当行为分支达到一定复杂度时，用策略、工厂或注册表来承接扩展。

适用判断：

- 分支少于 `3` 个时，优先简单 `if`。
- 分支达到 `3` 个以上且持续扩展时，再考虑策略模式或工厂模式。

## 6. 错误处理规范

- 底层模块抛出明确错误，不返回模糊失败。
- service 层要么返回稳定 `Result` 结构，要么抛出清晰的自定义错误。
- controller / route 层负责把内部错误映射成统一响应格式。
- 不吞错，不伪成功，不把真实失败隐藏成演示态成功。

默认目标响应形态：

```json
{
  "code": "NOT_FOUND",
  "message": "Document doc_xxx not found",
  "data": null
}
```

## 7. DRY（不要重复自己）

- 一份知识在系统中只保留一个权威定义。
- 公共验证规则、时间格式化、错误码、共享类型、环境配置都应集中。
- 提取公共逻辑时，抽取的是“同一份知识”，不是“长得有点像的代码”。

## 8. KISS（保持简单）

- 最简单、最清楚、最容易解释的实现通常是首选。
- 不提前抽象，不为了“未来也许会用到”增加层级。
- 能用数组就不急着上 `Map`，能用 `for` 就不急着上复杂链式变换。
- 复杂度要来自业务本身，而不是来自实现炫技。

## 9. 近模型规则

代码结构要尽可能贴近业务领域的自然模型，让业务专家也能看懂主要边界。

推荐方向：

- `entities/`：核心业务实体
- `value-objects/`：不可变值对象
- `repositories/`：数据访问抽象
- `services/`：领域服务或业务编排

命名要求：

- 不叫 `updateProfileData()`，优先 `approveProfileChange()`
- 不叫 `saveSchool()`，优先 `registerNewSchool()`

规则封装要求：

- 关键业务规则尽量放在拥有它的对象或服务附近
- 重要状态变化通过方法或显式流程触发，而不是直接外部改字段

## 10. 可读性与艺术性

- 变量名要表达意图，而不是缩写谜语。
- 函数名优先动宾结构，让读者看到名字就知道它做什么。
- 注释解释 `why`、边界、约束和权衡，不解释表面语法。
- 代码要有节奏：逻辑分块之间留空行，相似结构尽量对称，命名风格保持统一。
- “艺术性”不是花哨，而是让结构、命名、留白和控制流读起来顺。

## 11. 代码即文档

好的代码应该尽量自解释，注释只补充读者无法从语法直接看出的背景。

不推荐：

```ts
// 遍历数组
for (const item of items) { ... }
```

推荐：

```ts
// 因为缓存 TTL 只有 30 秒，这里不做强制刷新。
// 如果 TTL 提高到分钟级，需要把这里改成主动刷新策略。
```

## 12. 评审清单

### 架构思维

- 职责是否单一？
- 数据流是否清晰？
- 状态归属是否正确？
- 依赖方向是否正确？

### 可读性

- 变量名是否表达意图？
- 函数名是否清晰？
- 注释是否解释 why？
- 代码是否自解释？

### 艺术性

- 结构是否对称、统一？
- 是否有逻辑留白？
- 是否避免了噪音式注释和碎片化命名？

### 简洁高效

- 当前实现是否已经足够简单？
- 是否存在可提取的重复知识？
- 是否出现过早抽象或过度设计？

### 近模型规则

- 业务语言是否直接映射为代码？
- 规则是否封装在拥有它的对象或服务附近？
- 领域边界是否清晰？

## 13. 最终基线

本项目后续代码默认同时满足以下要求：

- 能跑通
- 可维护
- 数据流清晰
- 命名贴近业务
- 错误处理可靠
- 结构简洁且有美感

“代码可工作”只是起点；“代码可解释、可演进、可长期信任”才是基线。
